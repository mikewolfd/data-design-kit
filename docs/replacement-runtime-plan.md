## Decisions that constrain implementation

**Guard every supported selection path.** In the inspected native source, Refresh leaves `select_prepared_with_policy` before the Build quality guard; Backfill has a separate selection path. This is a hazard when widening support, not a demonstrated bypass of the qualified Build profile. Reuse those operations, add the appropriate native guard, and test every promised branch before advertising it. [Native completion code](/Users/mikewolfd/Work/worktrees/docspec-ddk-runtime/src/engine/pipeline/completion.rs).

**Bind qualification to the final composed candidate.** Backfill can combine retained work with a newer sibling state. The initial expanded profile must refuse a changed selection or composition while preserving useful native completions. Supporting that race later requires an explicit native transition that records the newly composed candidate, exposes its exact views, and obtains new qualification. Adding a guard alone is insufficient: the existing managed readback and policy cannot silently acquire a different candidate or expected selection.

**Version the new mapping behavior explicitly.** The current report shapes describe flat mappings. Resolve the successor schema/profile revision before changing them, using the existing extension mechanism where it can express a required capability faithfully. Keep frozen 0.1 reports interpretable under their original schemas. A native view identifies version, group, table metadata/snapshot/schema, and complete field-ID paths; a leaf ID or schema number alone is insufficient.

**Make multi-view qualification explicit before broadening the reader.** The existing native evidence names one candidate and one completed read; DDK quality selects one dataset. The successor policy must bind each required check instance to its complete target and reference-view set, including exact versions, groups/tables, schema interpretation, and required row/field coverage. Native acceptance verifies every associated completed read. Equal rule names on two groups are distinct obligations. Checking one cannot qualify both. Richer field metadata alone cannot establish which relations a cross-table query consumed.

**Accept evidence through two concrete verifier routes.** Keep the qualified DCC profile for its supported rules. Add a separately qualified native SQL report profile for the complete application-owned report inventory already executed by the native job. This route does not translate or claim equivalence with DCC rules. It verifies the original rules, trusted evaluator/version and semantics, exact candidate and complete target/reference-view set, completed execution and applicable reads, and every required outcome. Missing, duplicate, failed, unknown or not-run obligations prevent acceptance. Generic caller-supplied passed booleans cannot satisfy either verifier. Reuse qualifying native reports without exporting their candidate through Arrow into DuckDB merely to repeat those rules. The local-file native SQL acceptance implementation passes the complete DocSpec gate and bounded consumer checks; DDK native profile and complete application qualification remain required. Schema-only job preparation proves neither execution nor acceptance.

The verifier resolves a DocSpec-retained completion under the original operation/request identity and compares its actual input, result and output inventory. Caller-supplied serialized query results and hashes alone do not prove native execution. The application owns the conditional blocking-report inventory, separately from metadata reports such as facets and coverage. For Congress's aggregate-counter profile, each required report has exact query, column and integer-type membership, exactly one complete row, and zero for every required counter. Empty, null, duplicate or truncated results refuse; a truthiness reduction is insufficient. These are profile-specific semantics, not a universal shape for every SQL report.

**Keep quality semantics and resource claims separate.** For rules requiring DCC evaluation, the proposed bounded path streams Arrow batches once into a DuckDB temporary table so maintained checks can query the complete relation repeatedly. Qualify type preservation, complete ingress, actual spill, and all required checks on the pinned libraries. A DuckDB memory setting does not establish a whole-process bound. Custom SQL also needs bounded scalar results and the established read/function/effect restrictions. Native SQL evidence has its own execution and coverage proof; it does not inherit this route's resource or semantics claims. [DCC quality proposal](/Users/mikewolfd/Work/artifacts/ddk-replacements-20261106/shared-runtime/quality-access-plan.md).

**Separate temporary work from reusable completions.** Disposable evaluator scratch may be rebuilt after interruption. Retain a complete evaluator report before acceptance, and reconcile lost acceptance responses through DocSpec. Preserve expensive native computation independently of qualification changes. Any promise to resume completed evaluator materialization or checks needs an explicit native-owned completion; an application cache cannot supply that promise.

Retained SQL execution must preserve the application's existing dependency and last-consumer information. For each durable intermediate, name the saved recovery work, remaining consumers, native protection owner, and retirement condition. A materialized relation is not automatically a permanent checkpoint. Release disposable bulk when its consumer and recovery obligations end; retain the completion evidence required for reconciliation.

Bind every influential input into the whole-job reuse identity. An application's narrower output identity that intentionally excludes predecessor ledgers cannot stand in for that identity. Exact snapshot selectors and a process-local consumption context do not establish durable protection. Admission must establish custody for recovery, then map intermediate, result and operation lifetimes to the existing native retirement scopes and the remaining publisher/readback obligations.

**Admit acquisition before external effects.** Application-owned source policy and the existing native lifecycle must establish permission, capacity, input scope and a recoverable attempt identity before fetching or writing. Carry last-consumer obligations through computation, qualification, export, publication and readback. Native protection and retirement remain with the existing owner; a catalog or application wrapper must not introduce another controller.

**Separate material dependencies from complete provenance.** Congress's retained [fingerprint comparison](/Users/mikewolfd/Work/congressional-tech/.cache/archive-release/ddk-replacement-20261106/parser-lock-drift-02/fingerprints.json) shows that changing the whole `uv.lock` changes seven parser fingerprints and the filename-catalog fingerprint while their source owners remain unchanged. Restoring only the prior lock reproduces all eight declared pins. The entrypoint refusal is established; parser equivalence and retained-data compatibility are not. The successor needs an explicit, versioned interpretation of dependencies that affect each computation, qualification and metadata result, while retaining the full lock as provenance. Keep current guards until that interpretation is implemented and checked. Do not restamp retained rows, bypass the guard or require a blanket replay from this observation alone.

**Keep membership and activation distinct.** Native generation membership binds exact table versions; it does not atomically advance every table or external consumer. Update all application producers and readers together. Each new reader resolves one selected release root and uses its exact members. Each publisher retains its own conditional-write token and scope. Protect references still needed by new-stack execution, readers, or recovery.

The agreed publication policy preserves an accepted decision: once the native owner accepts the frozen intent, later native selection changes do not silently revoke it. External activation still requires the original expected publisher token. Define and implement that acceptance transition before effects; the policy is not yet runtime-qualified. Revocation semantics remain unsupported unless separately implemented. Bind durable publisher evidence to the original attempt and expected token. After a lost response followed by a successor publication, the current pointer alone cannot prove whether the original attempt committed. Preserve `unknown` when history cannot settle that question, and prevent an old attempt from replacing the successor.

Bind that publication decision to the original attempt, accepted native result, frozen artifact inventory and expected publisher token. Keep the existing publisher's conditional activation and reconciliation. Congress's [release assembly](/Users/mikewolfd/.codex/worktrees/9c45/congressional-tech/packages/viewer_publication/src/viewer_publication/archive_format.py) includes catalog bytes in release identity. Publication feedback therefore belongs to a separate later observation/discovery view that refers to the frozen release. Rewriting the selected catalog to include its own publication result would change that identity. This is a design constraint; no existing rewrite corruption has been demonstrated.

The examples below define full acceptance obligations. Application originals and independently authored expected values supply the oracle; the new transformation must not generate its own expected results. Narrower executed results are recorded separately in [verification](verification.md). Small cases establish mechanisms, while each application's complete source/consumer inventory determines replacement acceptance.

| Case | Required observation and planted failure |
| --- | --- |
| Shared content, separate occurrences | Two source occurrences share content. A meeting contains two identical sitting structs and another contains an empty sittings list. Preserve occurrences, repetition, order, empty versus null, fixed[32] bytes, and native IDs including meetings element 7 and sittings element 18. Changing one nested field ID must refuse. |
| Based correction and deletion | Start with occurrences o1/o2 sharing h1; append o3=h2; correct only o2 and explicitly empty its children; delete o3 from the current view. Preserve o1, raw history, and the exact prior release. Unmentioned rows in partial input remain present. |
| Completed work survives caller loss | Kill after an expensive native phase and lose the selection response. A fresh process reconciles the same operation, reuses completed work, and establishes one coherent result. Changed input under the same operation ID refuses. |
| Exact numeric and temporal meaning | Preserve fixed binary widths, decimal scale beyond Float64 precision, timestamp units/zones, source spelling, and null/empty statuses. Wrong width, rounding, deduplication, or an implicit timezone fails the applicable check. |
| Complete bounded evaluation | Increase the retained population while keeping the changed set and resource allocations fixed. Check row identity and nested counts, including a violation in the final batch. Wrong candidate, missing/duplicate check, truncated read, or lost protection prevents acceptance. Two groups with equal rule names but only one evaluated must refuse. Measure aggregate process memory, actual rows/bytes, and scratch. |
| Typed native SQL evidence | Accept the complete original report inventory for the exact retained candidate/view set without DCC re-materialization. Refuse wrong candidate/view membership, changed rules or evaluator, missing/duplicate outcomes and incomplete execution. DCC-only obligations remain unsatisfied by unrelated native reports. Verify that the managed catalog records the native accepted identity; file-backed evidence still passes its own verifier. |
| Changed candidate composition | Evaluate prepared B, then select sibling C. B's selection either refuses while preserving C or follows a separately qualified native transition to a new B+C manifest. Evidence for B's earlier manifest cannot authorize B+C. |
| Complete consumer release | Exercise the actual shared materializations and 23 congressional public tables, plus every required SpicyRegs publication scope. Missing or mixed members prevent activation. After response loss, recover through the existing publisher and verify API/MCP/browser/index readback against the selected root. Include an intervening successor publication; unresolved historical outcome remains unknown and never rewinds the successor. |
| Frozen release and later observations | Keep catalog and artifact bytes unchanged through activation and recovery. Record the observed publication in a separate view referencing the exact release. Exercise a later native authority change under the explicitly chosen decision-lifetime policy and a stale publisher token; unsupported transitions refuse before effects. |
| Material dependency interpretation | Change only a consumer metadata dependency, then a dependency that affects parsing. The versioned interpretation must identify the distinct obligations without dropping full provenance. Retained values and existing pins remain untouched until their reuse is established; unknown influence preserves refusal. |
| Reused inputs and coordinated consumers | Bind exact retained originals or native members to the new interpretation. Refuse wrong-table or missing-member mappings. Every updated consumer reads the same qualified new release; no legacy reader fallback is required. |
| Honest source coverage | Keep held, consumed, refused, emitted, and unselected occurrences distinguishable. A metadata refresh preserves unknown/partial coverage and opens no data payloads. |
